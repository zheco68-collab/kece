# KECE 评测机分池容量基线、灰度切换与只读对账报告

本报告保留 2026-11-07 的本地容量基线及其测量口径，并给出当前实现的上线与回滚门禁。生产切流记录应由实际部署人员填入运行版本、时间和只读证据。

## 1. 上线前的检查与回滚门禁

### 1.1 准入条件

1. 在独立环境演练 Flyway V26～V31 和制品目录备份。节点登记了 HTTPS 探测地址时，升级后重新自检。
2. 从管理员 API 按 `ALGO` 和 `DATABASE` 分别回填历史用例清单。每次最多 20 道。记录 `nextAfterId`，按 `more` 继续，对 `failures` 中的题目修复用例后重跑；最终从 `afterId=0` 复核剩余任务。保留回填失败和无法发布的空用例题目清单。新链路要求提交绑定非空清单。
   ```bash
   curl --fail-with-body -X POST "http://127.0.0.1:8080/api/v1/admin/judging/manifests/backfill?type=ALGO&afterId=0&limit=20" \
     -H "Authorization: Bearer $ADMIN_TOKEN"
   ```
3. 在目标机器按[节点手册](../deploy/judger/README.md)准备五池，记录每个节点的运行时版本、镜像摘要、宿主机总槽位和自检 ID。用真实题目验证各池接单，并检查公网入口对机器 API 的阻断。
4. 发布单须写入当前包和已验证的回滚包的不可变版本及校验值，包含后端、worker 和相容的数据库迁移范围。未登记可复现回滚包时暂停发布。

### 1.2 旧系统切到持久队列

从旧 Redis 评测系统迁移时，安排维护窗口并暂停新提交。保留旧 worker 消费到队列排空，核对旧编程／SQL 队列、旧结果队列以及业务提交的非终态计数。在切换运行版本前保存记录。保留历史终态结果和审计记录。

在旧 Redis 实例上只读核对这四个键，四项都应返回 `0`。连接参数以目标环境为准。

```bash
for key in judge:queue judge:sql:queue judge:results judge:sql:results; do
  printf '%s ' "$key"
  redis-cli LLEN "$key"
done
```

当前 PR-10 版本全部走持久链路，`PUT /api/v1/admin/judge-routes/{pool}/{scene}` 只更新持久路由的 revision。真正逐池切流需要能同时运行两套链路的已验证兼容包。记录每次切流的 pool、scene、route revision、node 版本、job ID 范围和对账输出。

### 1.3 当前版本回滚

1. 先暂停新提交，保持评测节点可领单，直到队列与结算事件归零。
2. 使用以下门禁保存证据。它要求全量不变量通过、没有 `QUEUED` / `RUNNING` 任务、结算事件全部 `DONE`。
   ```bash
   python scripts/reconcile-judge.py --url http://127.0.0.1:8080/api/v1 --require-drained --output pre-rollback.json
   ```
3. 排空后将节点置为 `DRAINING` 再停机，部署发布单中已验证的回滚包，检查控制面与业务 API 后恢复写入。若新任务无法排空，保留持久任务、清单和制品，先恢复能处理这些任务的节点；禁止复制到旧 Redis 队列或将任务人工标记完成。

## 2. 历史只读对账与 6 大核心不变量

### 2.1 核心不变量定义

| 编号 | 不变量名称 | 校验规则 | 实测违规数 |
| :---: | :--- | :--- | :---: |
| **I-1** | **业务指针一致性** (`orphanPointers`) | `submission.current_judge_job_id` / `db_submission.current_judge_job_id` 必须指向存在的 `judge_job`，且 `(submission_type, submission_id)` 双向吻合 | **0** |
| **I-2** | **单活动尝试排他** (`duplicateRunningAttempts`) | 任意 `judge_job` 在同一时刻最多只能有 1 条 `RUNNING` 状态的 `judge_job_attempt` | **0** |
| **I-3** | **终态收敛一致性** (`unconvergedCompletedJobs`) | 状态为 `COMPLETED` 的 `judge_job`，其关联业务提交不得停留在 `PENDING`/`JUDGING` 等非终态 | **0** |
| **I-4** | **失败终态一致性** (`mismatchedFailedJobs`) | 状态为 `FAILED` 的 `judge_job`，其关联业务提交必须收敛为 `SYSTEM_ERROR` | **0** |
| **I-5** | **节点与宿主机容量隔离** (`capacityViolations`) | 节点当前 `RUNNING` 任务数不得超过 `node.max_slots`，宿主机组汇总运行槽位数不得超过 `host_group.max_slots` | **0** |
| **I-6** | **结算事件无卡死** (`stuckSettlementEvents`) | `judge_settlement_event` 不得出现超时未消费或死信积压 | **0** |

### 3.3 实测指标分析

1. **API 接收高吞吐与低延迟削峰**：
   - 在每批 300 单、客户端并发 16 的测试中，后端持久化派单（含生成/复用 `judge_manifest`、写入 `judge_job`、更新 `current_judge_job_id`）吞吐稳定在 **581.54 ~ 707.98 req/s**，300 单两组的 P95 延迟为 **33.63 ~ 41.09 ms**，零失败、零拒绝。
2. **专池隔离与吞吐特征**：
   - `mysql` 专池通过进程内连接池创建临时独立 schema（`judge_<hex>`）并执行种子与比对，4 槽位下有效完成率达 **19.55 jobs/s**（300 单仅需 **15.349 s** 全部收敛）。
   - `python` 专池每次执行均拉起全新无网络只读 Docker 沙箱容器，4 槽位下有效完成率为 **3.78 jobs/s**，与 `mysql` 混合突发时互不抢占槽位，300 单混合突发（150 Python + 150 MySQL）在 8 槽位下于 **36.635 s** 全部收敛为 `ACCEPTED`。
3. **制品缓存命中与零共享目录**：
   - Go `judger` 通过 `GET /api/v1/internal/judgers/jobs/{jobId}/artifacts/{digest}` 下载测试点后缓存在节点本地 `cache/` 目录，同一题目的后续 299 次突发提交全部 100% 命中本地 SHA-256 校验缓存，零重复网络下载。
4. **租约自愈实测验证**：
   - 在混合池首轮 30 突发切换阶段，前一批次退出的旧节点曾短暂领走 2 个任务；后端 `JudgeMaintenance` 在 60 秒租约到期后自动将其重入队（`requeueExpiredLeases`），新节点立即接管并评测通过，末单在 `66.046 s` 收敛为 `ACCEPTED`，验证了节点掉线场景下的零人工干预自愈能力。

### 6.2 复测方法和适用范围

使用隔离的业务库、Redis 和判题 MySQL，并预先加载五池所需镜像。该脚本会创建题目、节点和提交。

```bash
python scripts/benchmark-judge.py \
  --url http://127.0.0.1:8080/api/v1 \
  --pools cpp,java,python,mysql,arkts --workloads 'mysql;python;python,mysql' \
  --smoke-pools --bursts 30,100,300 --concurrency 300 \
  --spawn-go-workers --judger-bin ./kece-judger \
  --nodes-per-pool 2 --slots-per-node 2 --output-json benchmark.json
python scripts/reconcile-judge.py --url http://127.0.0.1:8080/api/v1 \
  --require-drained --output reconciliation.json
```

压测 JSON 保存 HTTP 观察值。要复核排队时间，在隔离业务库按 `submission_type` 和 `submission_id` 关联下列只读导出。正式业务库如需执行此查询，应限制为本次批次的任务 ID 范围。

```sql
SELECT j.id, j.submission_type, j.submission_id, j.pool, j.route_revision, j.state,
       MIN(TIMESTAMPDIFF(MICROSECOND, j.created_at, a.started_at)) DIV 1000 AS queued_ms,
       TIMESTAMPDIFF(MICROSECOND, j.created_at, j.finished_at) DIV 1000 AS settled_ms
FROM judge_job j
LEFT JOIN judge_job_attempt a ON a.job_id = j.id
GROUP BY j.id, j.submission_type, j.submission_id, j.pool, j.route_revision,
         j.state, j.created_at, j.finished_at
ORDER BY j.id;
```
